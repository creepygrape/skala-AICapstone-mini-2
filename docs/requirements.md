## 1. 한 줄 소개

**정확한 대사나 영상 제목은 기억나지 않지만 장면의 상황을 어렴풋이 기억하는 팬(첫 적용 대상: NCT WISH 콘텐츠, 대상은 프로필로 교체 가능)이, 자연어 설명만으로 관련 영상의 재생 시점을 찾도록 돕는 근거 기반 AI Agent.**

### 1.1 사용자 문제와 기술적 제약을 구분한다

- **사용자 문제**: '마니또를 뽑다가 자기 자신을 뽑은 장면'처럼 상황만 기억한다. 일반 영상 제목/키워드 검색만으로는 정확한 장면을 찾기 어렵고, 영상을 직접 돌려보는 데 시간이 걸린다.
- **서비스 가치**: 장면 검색 결과를 영상/시간/근거 문구로 제공하고 바로 해당 시점으로 이동한다.
- **기술적 제약**: 실제 영상은 한국어·일본어 화면 자막을 포함하나, 확보한 추출 스크립트의 **언어는 영어**다. 추출 스크립트에는 공식 화자 라벨이 없고, 일부 영상에만 스크립트가 있다. 이는 사용자 Pain Point가 아닌 내부 데이터 처리 조건이다.
- **범위**: 음성·영상 자체를 이해했다고 주장하지 않는다. 실제 검색 대상은 수집·사용 가능한 SRT/TXT 및 그에 포함된 대사/화면 설명이다.

## 2. 확인된 입력 데이터 및 가정

| 항목 | 현재 확인 | 의사결정 |
|---|---|---|
| 첫 업로드 영상 | YouTube `1HJgbE66GI4` | 최초 통합 테스트 대상 |
| 업로드 SRT | 1,534개 자막 구간, 마지막 자막 종료 시점 약 01:01:23 | 원본으로 보존; 시간 코드 유지 |
| 함께 업로드한 TXT | 추출 스크립트의 텍스트형 보조 파일 | 가능하면 SRT 우선 |
| 추가 영상 | `camp_1.srt` (`vWjPXwKV_Y8`, 1,558 cue), `oth_5.srt` (`zOgJILPNzbE`, 658 cue) 확보 | 제목·이용 출처·영상 시간 정합성은 미확인; 로컬 manifest로 연결 |
| 스크립트 언어 | 영어 번역문 | 한국어 질문 → 다국어 의미 검색 / 필요 시 영어 검색어 재구성 |
| 화자 라벨 | 없음 | `speaker=null`; 멤버 이름 등장과 발화자 식별은 별개 |
| 괄호 속 화면 설명 | 존재. 예: `(RIKU chose RIKU)` | 검색 가치가 있어 원문 보존 |
| 자막 이용 | 외부 사이트에서 파일 추출 가능 | 접근·이용 약관과 저작권 검토. 전체 자막을 공개 저장소에 재배포하지 않음 |

### 2.1 검색 가능한 표현의 경계

- **발언 찾기**: '료칸이 뭔지 물었던 부분' → 02:15~02:20 부근.
- **상황 찾기**: '리쿠가 마니또 뽑다가 자기 자신 뽑은 장면' → 03:09의 화면 설명 `(RIKU chose RIKU)`.
- **불확실한 질문**: '료칸이 뭔지 누가 물었어?' → 관련 장면 제공은 가능하지만 발화자 단정 불가.
- **검색 범위 밖**: 영상의 표정·몸짓처럼 **스크립트에 기록되지 않은** 시각적 사실의 확정 답변.

## 3. 사용자 및 대표 시나리오

**주 사용자**: 자막이 있는 영상 콘텐츠(첫 적용 대상은 NCT WISH)를 본 경험이 있고, 특정 발언 또는 재미있는 장면을 다시 찾으려는 팬. 범위를 줄이기 위해 WISH로 시작했을 뿐 제품 정의가 특정 대상에 묶여 있지 않다([확장 계획](roadmap-and-design-notes.md)).

| ID | 입력 예시 | 기대 출력 |
|---|---|---|
| UC-01 | 마니또 뽑다가 자기 자신 뽑은 장면 | 해당 장면 후보, 자막/화면 설명 근거, YouTube 시점 링크 |
| UC-02 | 버스에서 감을 한국어로 뭐라 하는지 얘기한 부분 | 감/persimmon 관련 대화 구간, 앞뒤 문맥 |
| UC-03 | 료칸이 뭐냐고 물어본 부분 | 02:15 전후 검색 결과 |
| UC-04 | 버스에서 간식 나누던 부분 | 간식이 등장하는 문맥적 구간 후보 |
| UC-05 | 료칸 설명한 멤버가 누구야? | 자막만으로 확인 가능한지 표시; 모르면 `speaker_unknown` |
| UC-06 | 이번 영상에서 강아지 산책하는 장면 찾아줘 | 근거가 없다면 `not_found`, 유사 장면을 사실로 오인하지 않음 |
| UC-07 | (검색 후) 그 장면 바로 보여줘 | 결과 카드의 타임스탬프 링크로 이동; 후속 대화 상태 저장은 P1 |

위 예시는 실제로 존재하는 내용을 확인한 구간과 **테스트용 미확인 요청**을 구분한다. 최종 테스트 데이터셋에서 영상·구간 정답을 별도 수동 확정한다.

## 4. 범위와 우선순위

**이번 과제의 대상 범위**: 구현·데이터·평가는 NCT WISH 영상 3편(첫 적용 대상)으로 한정한다(사용자 확인 2026-10-21). 다른 대상으로의 확장(대상 프로필, 언어·형식)은 향후 계획이며 이번 과제에서 지원한다고 주장하지 않는다. 자세한 내용은 [roadmap-and-design-notes.md](roadmap-and-design-notes.md).

### 4.1 P0 — 제출과 시연에 필수

| ID | 요구사항 | 완료 기준 |
|---|---|---|
| FR-01 | SRT 파일 등록 및 파싱 | 시작/종료 초, 텍스트, 비디오 ID, cue ID 보존; 잘못된 행 예외 처리 |
| FR-02 | 자막 청킹·인덱싱 | **영상 간 혼합 없이**, 인접 자막을 15~30초 안팎의 구간으로 묶고 원본 cue 연결 유지 |
| FR-03 | 한국어 자연어 질문 | 한국어 질문을 수신하여 영어 스크립트에서 장면 후보 검색 |
| FR-04 | Baseline 키워드 검색 | BM25 기반 기본 검색 구현; 평가시 고정 입력 사용 |
| FR-05 | Hybrid Retrieval | Dense 검색 + BM25 결과를 통합하고 상위 후보 반환 |
| FR-06 | LangGraph Agent | Router/Planner → Search → Context → Validator → Finalize 경로가 실제 작동 |
| FR-07 | 동적 재검색 | 근거 불충분 시 검색어/전략 변경 **조건부 최대 2회**(최초 검색 포함 최대 3라운드); 충분한 근거 확보 시 조기 종료, 무한 루프 금지 |
| FR-08 | MCP Tool | `search_transcripts`, `get_scene_context`, `get_video_metadata` 중 최소 2개 이상을 실제 LangGraph에서 MCP로 호출. 3개 권장 |
| FR-09 | 근거 검증 | 비디오·타임스탬프·원문 인용 유효성은 코드로 검증; 의미적 적합성은 전담 Validator가 점검 |
| FR-10 | 화자 단정 방지 | `speaker=null`일 때 발화자를 확정하지 않음. 멤버 `mentioned`는 발화자와 구분 |
| FR-11 | 웹 UI | 질문 입력 → 제출 → 진행 상태 → 검색 결과 카드 → 영상 링크 클릭을 브라우저에서 시연 |
| FR-12 | FastAPI + SSE 백엔드 | 질문을 POST로 받고 구조화된 SSE 이벤트를 순차 전달하며 완료/오류 이벤트 처리 |
| FR-13 | SSE 프런트엔드 | 진행 단계 `routing/searching/validating/replanning` 표시, 결과 카드 렌더링, 오류 표시 |
| FR-14 | 결과 신뢰성 | 검증 전 답변 초안은 스트리밍하지 않음; 근거 부족이면 `not_found`/`unsupported`로 종료 |
| FR-15 | 오류 대응 | MCP/검색/모델 호출 예외를 구분해 타임아웃·제한된 재시도·부분 결과 또는 명확한 오류 표시 |
| FR-16 | LangSmith + 평가 | trace 연동 가능한 설정, 동일 질문 벤치마크 및 Before/After 실행 스크립트·결과 보고 |
| FR-17 | ADR 작성 | 중요한 아키텍처 선택 시 배경/대안/이유/부작용/재검토 기준을 `docs/adr/`에 기록 |
| FR-18 | 단위/통합 테스트 | SRT 파싱, 타임스탬프, MCP, 검색, Validator, SSE 이벤트 최소 회귀 테스트 |
| FR-19 | 모듈화 | UI / API / Graph / MCP / Retrieval / Evaluation 분리, 환경변수 및 실행 README |

**P0 완성의 의미**: 브라우저에서 실제 질문을 입력해, 업로드한 영상 자막을 검색하고 근거가 있는 시점 링크를 받을 수 있어야 한다. 콘솔에서 함수만 실행되는 것은 미완성이다.

MCP 구현은 공식 Python SDK 2.x (`mcp>=2,<3`)의 `MCPServer`를 사용한다. SDK 1.x로 다운그레이드하지 않으며 Tool/Resource/Prompt 기능과 로컬 stdio 구조를 유지한다. Resource/Prompt 확장의 우선순위는 아래 P1을 유지한다. LangGraph 노드와 MCP 클라이언트의 연동은 설치 버전에서 검증한다.

### 4.2 P1 — P0 안정화 후 선택

- 서로 다른 영상/시점의 발언 비교(발화자의 동일성 단정 불가).
- 명확한 대화 후속 질문 및 SQLite checkpointer를 이용한 세션 영속화.
- Dense/BM25 실제 병렬 실행과 모델 티어링 비용 실측 최적화.
- MCP Resource(영상 카탈로그)/Prompt(검색 절차) 확장.
- 관리자용 자막 파일 업로드 페이지, 사용자 검토 화자 태그.

### 4.3 P2 — 범위에서 제외

- 모든 YouTube 영상의 실시간 크롤링, 실시간 자동 수집, 음성 자동 인식, OCR 자동 처리, 자동 화자 분리, 비디오 프레임 내용 이해.
- 제삼자 계정 로그인, 소셜 공유·커뮤니티, 복잡한 UI 디자인.
- 전 그룹/전 엔터테인먼트 검색, 무제한 Agent 루프, 다중 서버 운영 환경.

## 5. 핵심 화면 요구사항

단일 페이지를 기본으로 한다.

1. **Header**: WISH FINDER, 등록된 영상 수 또는 데이터 기준 안내.
2. **Question Composer**: 한국어 자연어 질문 입력, 예시 질문 칩 3개, 검색 버튼(로딩 시 중복 제출 방지).
3. **Live Progress**: SSE로 수신한 진행 상태 단계를 덮어쓰지 않고 누적 노출하며 단계별 소요 시간을 표시. 숨겨진 내부 추론 내용은 표시하지 않음.
4. **Result Cards**: 제목, 시작 시간, 짧은 실제 원문, 한국어 맥락 요약, 근거 종류(`dialogue` / `editorial` / `mixed`), 페이지 내 YouTube 임베드 재생('여기서 재생')과 보조 'YouTube에서 열기' 링크(임베드 차단 시 폴백).
5. **Fallback**: 검색 결과 없음, 화자 미확인, 일부 도구 오류 등의 상태를 명시.
6. **Accessibility**: 텍스트 대비, 키보드 버튼 작동, 외부 링크 안내.

프런트엔드 기술: **Vue 3 + Vite** 제안. Repository 탐색 단계에서 중대한 호환 문제가 있으면 변경 안을 보고하고 사용자 승인 후 수정.

## 6. API/이벤트 최소 계약

### 6.1 요청

`POST /api/search/stream` — `Content-Type: application/json`, `Accept: text/event-stream`

```json
{"query":"리쿠가 마니또 뽑다가 자기 자신 뽑은 장면","thread_id":null}
```

`GET /api/videos` — 등록 영상 목록/메타데이터 반환.
`GET /health` — API 생존 확인. 외부 모델/인덱스 상태는 별도 readiness 상태가 필요할 수 있음.

### 6.2 SSE 이벤트

이벤트 이름: `routing`, `searching`, `validating`, `replanning`, `result`, `error`, `done`.

```text
event: searching
data: {"request_id":"<uuid>","message":"관련 장면을 찾고 있어요.","attempt":0}

event: result
data: {"request_id":"<uuid>","status":"found","results":[{"video_id":"1HJgbE66GI4","start_seconds":189,"end_seconds":191,"evidence_text":"(RIKU chose RIKU)","evidence_type":"editorial","speaker":null,"url":"https://www.youtube.com/watch?v=1HJgbE66GI4&t=189s"}]}

event: done
data: {"request_id":"<uuid>","status":"found"}

```

`attempt`는 최초 검색 0, 첫 재검색 1, 두 번째 재검색 2다. `replanning` 이벤트는 필요한 경우에만 최대 2회 발생한다.

이는 **스키마 예시**이고 첫 이벤트/결과는 실제 검색을 통해 생성해야 한다. 이벤트 순서는 검색 경로에 따라 달라질 수 있으나, 최종 이벤트는 `result` 또는 `error`와 `done`을 구분해 처리한다.

- 브라우저에서는 `EventSource`가 아닌 **`fetch` + ReadableStream**을 사용한다(POST 본문 필요).
- 예외적으로 네트워크가 끊기면 `done`이 수신되지 않을 수 있으므로 프런트는 연결 종료/시간 초과도 처리한다.
- `status`: `found | ambiguous | not_found | unsupported | partial | error`.

### 6.3 결과 필수 데이터

- `video_id`, `title`, `start_seconds`, `end_seconds`, `url`
- `evidence_text`(실제 자막에 존재하는 문자열), `evidence_type`
- `speaker`(확인되지 않으면 `null`), `speaker_status`
- `explanation_ko`(근거로 확인되는 범위의 요약)
- `search_attempts`(실제로 실행한 검색 라운드 수, 검색하지 않으면 0, 최대 3), `status`, `request_id`
- 모델의 주관적 관련성 점수를 제공한다면 확률처럼 표현하지 않음.

## 7. 비기능 요구사항

- **안전성**: 원문에 없는 인용 문장/발화자/시간 생성 금지. 검증 실패 결과는 사용자에게 표시하지 않는다.
- **성능**: 초기 목표는 질문 후 15초 이내 완료(로컬 환경 목표, 실측 후 재조정). 첫 SSE 진행 이벤트는 2초 이내 목표. 기기·모델에 따라 차이가 있음을 보고.
- **비용**: 유료 API 사용은 명시적 사용자 허가가 있어야 한다. 기본은 로컬 또는 사용자가 이미 승인한 설정. 사용자 승인에 따라 개발은 로컬 Ollama, 시연·결과 제출은 OpenAI(`WISH_LLM_BACKEND=openai`)를 사용하며, OpenAI 모드는 질문과 후보 자막 일부(최대 3구간, 20초 문맥)를 전송한다(ADR-0008).
- **보안**: API 키 `.env`, `.gitignore`; 자막 데이터 접근 경로가 외부 사용자 입력으로 임의 지정되지 않도록 제한.
- **저작권/데이터 사용**: 수집처 이용 조건 준수, 원본 영상 링크와 짧은 근거만 UI에 표시. 전체 외부 자막의 공개 저장소 재배포는 피하고 로컬 데이터 경로 지원. 평가용 합성 fixture 별도 관리.
- **검증 가능성**: 동일한 데이터/질문/모델 설정으로 평가 결과 재생산; 임베딩 모델/인덱스 빌드 기준 기록.

## 8. 정량 평가 정의

### 8.1 비교 대상

- **A**: 단일 키워드 검색(BM25). 단독 검색의 한계를 보여 주되, 한국어→영어 표현 차이의 영향을 별도 설명한다.
- **B**: 동일 데이터에서 BM25 + Dense + 고정된 Fusion 사용(재계획/검증 없음).
- **C**: B + Agent의 의도 추출, 최대 2회 재검색, 근거 검증.
- **공정한 추가 비교**: B와 C에 동일한 초깃값의 정규화된 검색어를 주어 **Agent 재검색·검증 자체의 효과**도 별도 확인한다. A/B/C가 다른 모델/번역비용을 쓰면 이를 조건표에 밝힌다.

### 8.2 필수 지표

| 지표 | 정의 |
|---|---|
| Hit@3 / Recall@3 | 정답 영상의 허용 정답 시간 구간과 겹치거나 허용 오차(기본 ±10초) 내인 결과가 Top 3에 있는 비율 |
| Scene Success@1 | Top 1 결과의 해당 영상/시간이 정답 조건을 충족한 비율 |
| Unsupported Accuracy | 화자 미식별/스크립트 외 질문에서 알 수 없음을 정확히 고지한 비율 |
| Unsupported Hallucination | 근거 없이 화자를 단정하거나 없는 발언·시간을 만들어낸 건수 |
| Latency | 질문당 총 응답시간 평균·p95(소표본임을 명시) |
| Attempts / Tool Calls | 재검색 횟수, 도구 호출 횟수 |

### 8.3 최소 평가셋

- 총 20~30문항을 **실제로 업로드한 자막을 읽고 수동 레이블링**한다.
- 유형: 직접 표현/키워드, 모호한 장면 기억/의역, 복수 후보, 근거 없음, 화자 미확인.
- 정답은 `expected_video_id`, `accepted_intervals[]`, `answerability`, `evidence_cue_ids[]`로 기록. 여러 정답 구간 허용.
- 예: `RIKU chose RIKU`(03:09), `Ryokan ... what's a Ryokan?`(02:18), `What's 'kaki' in Korean?`(02:03) 등 첫 파일에서 확인된 후보.
- 학습용/데모용 질문을 최종 평가 데이터와 구분한다. 검색 파라미터 조정에 평가 데이터 답을 반복 사용하지 않는다.
- **목표 수치는 가설**: 최종 C가 B보다 Scene Success@1 또는 Unsupported Accuracy 개선. 수치 성공을 미리 보장하지 않는다.

## 9. 테스트 및 인수 기준

- AT-01: SRT 1,534개 구간을 손실 없이 파싱하고 타임스탬프/원문 보존을 확인한다.
- AT-02: 한국어 상황 질문으로 03:09의 마니또 장면을 실제 영상 링크와 함께 찾는다.
- AT-03: '료칸이 뭔지 물었던' 질문에서 실제 02:15~02:20 부근이 후보로 검색되는지 점검한다.
- AT-04: '누가 말했다'는 질문에서 검증 불가능한 화자를 임의로 확정하지 않는다.
- AT-05: 자막에 근거가 없는 요청은 `not_found` 또는 `unsupported`로 종료한다.
- AT-06: 웹에서 질문 입력 후 SSE 상태 업데이트와 결과 카드 표시가 실제로 동작한다.

- AT-08: C에 대해 A/B와 동일 고정 질문셋으로 성능 비교표를 생성한다.
- AT-09: 실행 명령, 환경변수 예시, ADR, 트레이드오프, 회고에 필요한 실험 기록이 남는다.
