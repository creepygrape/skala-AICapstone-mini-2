# ADR-0011 — 첫 검색에서 Router 검색어와 사용자 원문을 함께 검색 (이중 첫 검색)

상태: Proposed (구현·단위 테스트·실제 코퍼스 단발 확인 완료, **gold 정량 평가 전** — 기본값 off)

## 배경
같은 의미의 질문이 문구에 따라 `found`/`not_found`로 갈렸다. 실제 trace로 확인한 원인은 Router(LLM)가 만든 영어 검색어가 번역 자막의 어휘와 다르다는 것이다("manitto"로 검색했지만 자막은 "Secret Santa"). 같은 질문을 **한국어 원문 그대로** Hybrid 검색에 넣으면 다국어 임베딩(bge-m3)이 정답 cue를 1위로 찾았다. 즉 Router의 어휘 실수를 원문 검색이 보완할 수 있다. 기존 통제 실험에서도 C(Router 영어)와 C-ko(한국어 원문)가 같은 16/18이었다(day2-eval-openai).

## 결정
- 첫 라운드(`attempt=0`)에 `search_transcripts`를 두 번 호출한다: Router 검색어, 사용자 **원문**. 두 목록을 **순위별로 번갈아(Router 우선) 채워** 합치고, 기존과 같은 최대 3개(+exclude)만 근거 확인·판정으로 보낸다. 후보의 식별 기준은 청크가 아니라 **근거 cue(영상 + `selected_cue_id`)**다. `selected_cue_id`는 검색어별로 고르므로 같은 청크에서 두 검색이 서로 다른 cue를 고르면 둘 다 후보로 남기고, 두 검색이 같은 cue를 고르면 한 칸만 쓴다. 서로 다른 청크가 겹치거나 시작이 10초 이내면 기존 검색기처럼 하나만 남긴다. `score`는 RRF(k=60) 합으로 trace용이다. 판정 호출 수와 OpenAI로 보내는 후보 수(최대 3구간)는 그대로다.
- **재검색 라운드는 기존대로 단일 검색**이다(재작성은 검색어를 바꾸는 것이 목적). 원문으로 실제 검색했으면 `queries` 이력에 넣어 재작성이 같은 검색어를 반복하지 않게 한다.
- **건너뛰는 경우**: 원문이 Router 검색어와 같을 때, 후속 질문(`resolved_query`가 있음 — 원문이 "다른 장면도" 같은 지시어뿐), unsupported/chat(검색 없음).
- 두 번째 검색이 실패하면(`SearchFailure`) 첫 검색 결과로 계속한다(trace에 기록). 첫 검색 실패는 기존대로 오류다.
- 플래그 `WISH_DUAL_QUERY=1`(기본 off). `FinderAgent(dual_query=...)`로 주입하고 API와 평가 하네스(`eval.run_eval`, 결과 JSON의 `dual_query`)가 같은 환경변수를 읽는다. 인용·시각·URL은 여전히 원문 cue에서 결정적으로 만들며 후보 검색만 넓어진다.

## 합치기 방식의 변경 이력
- v1: 청크 ID 키 + RRF 점수 합. PR #13 리뷰(P1)가 지적: 같은 청크의 `selected_cue_id`가 검색어별로 다른데 `setdefault`로 Router 쪽 cue만 남겨, 원문 검색이 고른 실제 cue가 버려진다.
- v2: 키를 근거 cue로 변경하고 RRF 합 정렬 유지. **실제 코퍼스에서 회귀를 발견했다**: 두 검색이 함께 고른 약한 후보("(Grilled squid) I want this too", 판정 uncertain)가 합산 점수로 1위가 되어 3칸 중 한 칸을 차지하고, Router의 2위였던 정답(45:53)이 밀려났다("구운 오징어" 질문이 기능 off 4/4에서 45:53, v2 on 3/3에서 42:41). 합산 정렬은 "가장 그럴듯한 후보"에는 맞지만 목적은 "판정 3칸 안에 정답을 넣는 것"이다.
- v3(현재): 순위 교차 채우기. 각 검색의 상위 후보가 보장되고 공유 cue는 칸을 절약한다. 같은 입력(LLM 없이 같은 두 검색 결과)에서 v2는 정답을 3칸 밖으로 밀었고 v3는 안에 넣었다.

## 대안/트레이드오프
- Router 모델을 `gpt-4o`로 올리기: 코드 변경이 없지만 토큰 비용이 늘고, 문구 민감성의 근본 원인(번역 어휘)은 남는다. 별도 선택지로 유지.
- Router가 대체 뜻 검색어(`alt_queries`)를 내게 하기: 이미 시험했고 gpt-4o-mini가 목록을 비워 발동하지 않아 폐기(roadmap §6).
- **비용**: 검색이 두 번이라 첫 라운드 지연이 늘고(실제 코퍼스 단발 관측: 질문당 약 +1~2초), MCP 도구 호출이 질문당 1회 늘어난다. LLM 호출·토큰은 늘지 않는다. 검색 게이트가 동시 실행 1건이라 순차 실행이다.
- 한국어 원문이 약한 질문에는 도움이 없고, 원문 검색의 상위 후보가 한 칸씩을 차지하므로 Router 쪽 3위 이하 후보는 3칸에서 빠진다(미측정). 같은 청크의 서로 다른 cue가 두 칸을 쓰면 비슷한 시각의 카드가 둘 보일 수 있다.
- 판정 후보 수를 늘리면(예: 4~5개) 포함 확률은 오르지만 판정 토큰과 OpenAI 전송 범위(ADR-0008의 최대 3구간)가 늘어서 채택하지 않았다.

## 결과 / 검증
- 단위 테스트 11개 추가(기본 off, 첫 라운드만 두 검색어, 재검색은 단일, 원문 이력 반영, 동일 검색어·후속 질문·unsupported 건너뜀, 두 번째 검색 실패 시 폴백, 같은 청크의 다른 cue 보존, 공유 cue 한 칸·점수 합, 공유된 약한 후보가 2위를 밀어내지 않는 회귀, 겹치는 청크 중복 제거). 백엔드 전체 164 통과·1 skip.
- 실제 코퍼스 단발 확인(OpenAI, 질문당 1회, **gold 평가 아님**): 기능 off에서 `not_found`(3라운드, 약 8초)였던 마니또 질문 두 문구가 on에서는 둘 다 1라운드에 정답 시점(3:09)을 `found`로 반환했다. v3 기준으로 장면 질문 10건(마니또 2문구, 료칸, 오징어 ×2, 김치찌개, 곰·물고기, 4월 20일 앨범, 한우 축제)이 모두 `found`였고 범위 밖 질문은 그대로 거부했다. 오징어는 사용자가 확인한 45:53, 마니또는 3:09, 료칸 2:18, 곰 58:04, 앨범 34:46, 한우 0:39를 반환했다. 김치찌개는 이번에 8:37(같은 코퍼스의 다른 관련 장면)이 1위였고 사용자 확인 시점(10:33)은 아니었다(기능 off 단발에서도 8:37이 1위였던 적이 있다).
- **미측정**: gold 20문항 A/B/C 재측정(정확도·지연·호출·토큰), 확신 오답 증감, 반복 분산. 이 결과 전까지 기본값을 켜지 않는다.

## 재검토 조건
gold 재측정에서 Scene Success@1이 오르지 않거나 확신 오답이 늘면 철회하거나 off로 유지한다. 개선이 확인되면 기본값을 on으로 바꾸고 이 ADR을 Accepted로 갱신한다.
