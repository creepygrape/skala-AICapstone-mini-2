# WISH FINDER 발표 대본

슬라이드의 발표자 노트와 같은 내용입니다. make_ppt.py가 pptx와 함께 생성합니다.

## 1번 — 광주 3반 G078 문희주 · WISH FINDER

안녕하세요, 광주 3반 G078 문희주입니다. 주제는 영상 속 장면이 어렴풋이만 기억날 때, 그 장면을 설명하면 영상의 정확한 시점을 찾아 주는 AI Agent입니다.

## 2번 — 장면을 설명하면, 원본 자막으로 검증한 시점을 찾아 준다

팬들은 "A가 이런 말 하지 않았나요"처럼 대략적인 내용만 기억하고 출처나 정확한 표현을 기억하지 못하는 경우가 종종 있습니다. 그래서 장면을 설명하면 원본 자막으로 검증한 영상 시점을 알려 주는 Agent를 만들었습니다. 세부 task는 청킹, Hybrid 검색, LangGraph, MCP, 웹 뷰, 평가입니다. 자막 데이터는 영어 스크립트고, 화자 표시가 없어 화자는 단정하지 않습니다.

## 3번 — 결과: 16/18을 맞혔고, 근거 없는 화자 단정은 0건

평가는 20문항으로 했습니다. 장면을 찾는 질문이 18개, 자막으로 알 수 없는 요청이 2개입니다. 비교 대상은 세 가지로, A는 키워드 검색, B는 Hybrid 검색, C는 Hybrid에 검증과 재검색을 더한 Agent입니다.

장면 질문 18개 중 1위로 정답을 맞힌 수는 A가 13개, B가 15개, C가 16개입니다. 다만 아직 데이터가 작고 한 번만 실행해서 C가 낫다고 단정할 수는 없습니다.

개선한 v3는 네 가지를 고쳤습니다. 화자 질문의 판정 기준을 완화하고, 번역 자막의 단어 차이에 대응하고, 중복 재검색을 없애고, 검색어 재작성을 개선했습니다. 그 결과 화자 질문 처리가 2개에서 3개로 늘고 LLM 호출이 16% 줄었습니다. 반면 입력 토큰은 15% 늘었고, 틀린 장면을 찾았다고 답한 사례가 1건 생겼습니다. 근거 없이 화자를 단정한 경우는 0건입니다.

이중 첫 검색은 켜도 꺼도 결과가 같아 꺼 두었고, 청크는 20초와 10초를 유지했습니다. 한계는 후속 질문과 번역 어휘 차이, 그리고 Multi-Agent를 구현하지 않은 점입니다.

- 화자 유무 기준 완화(화자를 몰라도 장면 찾아줌)
- 번역 자막 대응(뜻이 같으면 같은 장면, 검색어와 비슷한 말, 멤버 이름 사전 추가)
- 중복 재검색 제거(이미 확인한 결과는 pass)
- 검색어 재작성(실패한 예를 보여주고, 다른 방향으로 작성)

## 4번 — LangGraph · MCP · RAG를 하나의 흐름으로 엮었다

전체 구조입니다. 화면의 질문은 FastAPI를 거쳐 LangGraph Agent로 가고, Agent는 MCP 서버를 통해서만 자막을 조회합니다. 자막 검색은 키워드와 의미 검색을 합친 Hybrid 방식입니다.

## 5번 — Agent Graph: 경로는 코드가, 판단은 LLM이

Agent Graph입니다. 코드를 보면 StateGraph에 분류, 검색, 원본 대조, 판정, 재검색, 정리 여섯 노드를 add_node로 등록합니다. 다음 노드는 add_conditional_edges의 조건 함수가 정합니다.

이 그래프에는 갈림길이 세 개 있습니다.
첫 번째는 분류 후 질문이 자막으로 알 수 없는 요청이거나 일상 대화면 검색하지 않고 바로 정리 단계로 갑니다. 그 외에는 검색으로 갑니다.

두 번째는 판정 후, 관련 있는 후보가 나왔으면 정리로 가고, 없을 때만 재검색 여부를 확인합니다. 이 함수가 can_replan이 참인지 보는데, 횟수가 남았고 시간이 충분할 때만 재검색으로 보냅니다.

세 번째는 재검색 뒤입니다. 새로 시도할 검색어가 없으면 정리로 가고, 있으면 다시 검색으로 돌아갑니다. 이렇게 순환이 생기지만 MAX_REPLAN_ROUNDS가 2라서 두 번을 넘지 않습니다.

이 갈림길의 판단은 모두 LLM이 아니라 코드의 조건문이 합니다.
LLM이 판단하는 곳은 분류, 판정, 검색어 재작성 세 군데뿐이고, 인용과 타임 스탬프는 코드가 원본 cue에서 만듭니다.

## 6번 — MCP: 자막은 도구로만 접근하고, 검증은 원본 cue로 다시 한다

MCP는 읽기 전용 도구 네 개를 만들었습니다. Agent는 검색과 원본 조회 두 개를 쓰고, 나머지 두 개는 화면용입니다. search_transcripts가 준 청크는 가공된 텍스트라서, 인용과 시각은 get_scene_context가 돌려주는 원본 cue로 다시 확인합니다.
검색 도구는 질문, 검색 방식, 후보 수를 받는데 기본은 하이브리드 검색에 후보 세 개입니다.
설명에 "답이 아니라 후보"라고 적은 것처럼, 검색은 후보 청크와 대표 cue 번호만 돌려줍니다. 청크는 자막 여러 줄을 이어 붙인 검색용 텍스트라서 그대로 인용하기 어렵습니다. Agent는 두번째 도구를 이용해 영상 ID와 시각으로 원본 자막을 얻습니다.

## 7번 — RAG: 두 검색을 RRF로 합치고 원본 cue로 되돌린다

마지막 RAG입니다. 자막 3,750줄을 영상별로 20초씩 10초 겹치게 묶어 청크 869개를 만들고, 키워드 인덱스와 의미 벡터는 서버가 시작할 때 한 번만 만들어 재사용합니다. 키워드 검색 상위 20개와 의미 검색 상위 20개를 순위가 높을수록 큰 점수를 주는 RRF로 합치고, 점수 순으로 정렬해 겹치는 후보를 걸러 상위 세 개만 남깁니다.
마지막으로 각 후보 청크 안의 자막 줄마다 원문과 질문의 유사도를 구해 가장 가까운 한 줄을 대표 cue로 고르고, 그 번호를 후보에 붙여 돌려줍니다. 원문과 시각은 Agent가 이 번호로 가져옵니다.

코드 : 키워드 검색과 의미 검색이 각각 만든 상위 스무 개 순위를 합칩니다. 순위가 r인 후보에 1 나누기 60 더하기 r 점수를 주고, 두 목록에 모두 나오면 더합니다. 두 방식이 모두 높게 본 청크가 위로 오므로, 점수 순으로 정렬한 뒤 겹치는 후보를 걸러 상위 세 개만 남기고, 각 후보에서 질문과 가장 가까운 자막 한 줄을 대표 근거로 고릅니다. 마지막으로 이 세 개만 원본 자막으로 다시 확인합니다.

## 백업 — [백업] 이중 첫 검색: 번역 어휘 차이를 질문 원문 검색으로 보완

[백업] 질문 대비: 이중 첫 검색. Router 검색어가 번역 어휘와 달라 못 찾던 질문을, 질문 원문도 함께 검색해 보완한 시도입니다. 구현 중 점수 합산 방식에서 정답이 밀리는 문제를 실제 자막으로 확인해 순위 교차 방식으로 바꿨습니다. 정답 평가셋 20문항으로 끈 실행과 켠 실행을 다시 측정했더니 1위 적중이 둘 다 16개로 같았고, 못 찾은 두 문항도 그대로였습니다. 검색만 80회에서 98회로 늘었고 LLM 호출과 토큰은 같아서 기본값은 꺼 두었습니다. 마니또처럼 못 찾던 질문이 찾아진 것은 평가셋 밖 직접 실행에서만 확인했습니다.
