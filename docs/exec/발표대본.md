# WISH FINDER 발표 대본

슬라이드의 발표자 노트와 같은 내용입니다. make_ppt.py가 pptx와 함께 생성합니다.

## 1번 — 광주 3반 G078 문희주  ·  WISH FINDER

[10초] 안녕하세요, 광주 3반 G078 문희주입니다. 제 과제는 WISH FINDER입니다. 영상 속 장면이 어렴풋이만 기억날 때, 그 장면을 설명하면 영상의 정확한 시점을 찾아 주는 AI Agent입니다.

## 2번 — 장면을 설명하면, 원본 자막으로 검증한 시점을 찾아 준다

[40초] 팬들은 "A가 이런 말 하지 않았나요"처럼 대략적인 내용만 기억하고 출처나 정확한 표현을 기억하지 못하는 경우가 종종 있습니단. 그래서 장면을 설명하면 원본 자막으로 검증한 영상 시점을 알려 주는 Agent를 만들었습니다. 세부 task는 청킹, Hybrid 검색, LangGraph, MCP, 웹 화면, 평가입니다. 자막 데이터는 영어 스크립트고, 화자 표시가 없어 화자는 단정하지 않습니다.

## 3번 — 결과: 16/18을 맞혔고, 근거 없는 화자 단정은 0건
!!! 수정 !!!

[60초] 이전 장표에 나온 평가???? 장면 질문 18개 중 1위로 정답을 맞힌 수는 키워드 검색 A가 13개, Hybrid 검색 B가 15개, 검증과 재검색을 더한 Agent C가 16개입니다. 차이가 작고 한 번만 실행해서 우위는 단정하지 않습니다. 개선한 v3는 화자 질문 판정 기준, 번역 자막 대응, 중복 재검색 제거, 검색어 재작성을 고쳤습니다. 그 결과 화자 질문 처리가 2개에서 3개로 늘고 LLM 호출이 16% 줄었지만, 입력 토큰은 24% 늘고 틀린 장면을 찾음으로 답한 사례가 1건 생겼습니다. 근거 없는 화자 단정은 0건입니다. 이중 첫 검색은 켜도 결과가 같아 꺼 두었고, 청크는 20초와 10초를 유지했습니다. 한계는 후속 질문과 번역 어휘 차이, Multi-Agent 미구현입니다. 이제 구조와 핵심 코드를 설명드리겠습니다.

## 4번 — LangGraph · MCP · RAG를 하나의 흐름으로 엮었다

[20초] 전체 구조입니다. 화면의 질문은 FastAPI를 거쳐 LangGraph Agent로 가고, Agent는 MCP 서버를 통해서만 자막을 조회합니다. 자막 검색은 키워드와 의미 검색을 합친 Hybrid 방식입니다. 이제 핵심 코드 세 가지, Agent Graph와 MCP, RAG를 설명드리겠습니다.

## 5번 — Agent Graph: 경로는 코드가, 판단은 LLM이

[65초] Agent Graph입니다. 코드를 보면 StateGraph에 분류, 검색, 원본 대조, 판정, 재검색, 정리 여섯 노드를 add_node로 등록합니다. 다음 노드는 add_conditional_edges의 조건 함수가 정합니다. 분류에서 자막으로 알 수 없는 요청이면 곧바로 정리로 가고, 판정에서 관련 후보가 없고 시간이 남아 있을 때만 재검색으로 갑니다. MAX_REPLAN_ROUNDS가 2라서 재검색은 최대 두 번입니다. LLM이 판단하는 곳은 분류, 판정, 검색어 재작성 세 군데뿐이고, 인용과 시각은 코드가 원본 cue에서 만듭니다. Multi-Agent가 아닌 단일 워크플로입니다.

## 6번 — MCP: 자막은 도구로만 접근하고, 검증은 원본 cue로 다시 한다
!!! 수정 !!!

[50초] MCP입니다. 공식 SDK 2.x의 MCPServer에서 server.tool 데코레이터로 읽기 전용 도구 네 개를 만들고, 로컬 프로세스로 띄워 stdio로 통신합니다. Agent는 검색과 원본 조회 두 개를 쓰고, 나머지 두 개는 화면용입니다. 핵심은 검색 결과를 그대로 믿지 않는 것입니다. search_transcripts가 준 청크는 가공된 텍스트라서, 인용과 시각은 get_scene_context가 돌려주는 원본 cue로 다시 확인합니다. 검색은 계산이 무거워 동시에 한 건만 실행하도록 제한했습니다.

## 7번 — RAG: 두 검색을 RRF로 합치고 원본 cue로 되돌린다
!!! 수정 !!! ~ 기본값 + 청크 비교 수치? + 마무리?

[55초] RAG입니다. 자막 3,750줄을 영상별로 20초씩, 10초 겹치게 묶어 청크 869개를 만들었습니다. 키워드 검색 상위 20개와 의미 검색 상위 20개를 RRF로 합치는데, 순위가 r인 후보에 1 나누기 60 더하기 r 점수를 주고 더합니다. 청크는 cue 번호를 가지고 있어 결과가 항상 원본 자막 줄로 돌아갑니다. 청크 길이는 10초 5초, 30초 15초, 40초 20초와도 비교했고 20초 10초를 유지했습니다. 가장 크게 배운 것은 같은 질문도 표현에 따라 결과가 달라져서, 한 번 잘 나온 결과를 믿지 말고 측정으로 확인해야 한다는 점입니다.

## 백업 — [백업] 한계와 트레이드오프

[백업] 질문 대비: 한계와 트레이드오프. 측정, 성능, 비용·범위 세 갈래로 정리합니다. 측정은 18문항에 질문당 1회라 1에서 2문항 차이는 우연일 수 있고, 정답 라벨은 어시스턴트가 원본 자막을 검토해 제안하고 제가 승인한 것이며 영상 대조는 9곳 표본입니다. 성능에서는 찾음 응답 17건 중 1건이 틀린 장면이었고, 정답 청크가 후보 3개 밖에 있던 문항이 두 개 있었습니다. 비용은 입력 토큰이 24% 늘고 평균 지연이 2.6초입니다. 범위로는 Multi-Agent를 구현하거나 비교하지 않았고, 영어 번역 자막이라 화자를 단정할 수 없습니다.

## 백업 — [백업] LangSmith로 노드별 시간·LLM 호출·토큰을 추적했다

[백업] 질문 대비: LangSmith 추적. 평가 두 번의 합계가 트레이스 160개, 모델 호출 188회, 토큰 135.5K, 비용 $0.30입니다. 재검색이 있으면 지연·LLM 호출·토큰이 대략 두 배가 됩니다.

## 백업 — [백업] 의존성 주입과 테스트

[백업] 질문 대비: 의존성 주입과 테스트. FinderAgent는 모든 의존성을 생성자로 받고 테스트에서는 가짜 모델과 가짜 연결을 넣습니다. 모델 호출을 가짜로 대신해 과금이 없고 결과가 항상 같습니다.

## 백업 — [백업] 이중 첫 검색: 번역 어휘 차이를 질문 원문 검색으로 보완

[백업] 질문 대비: 이중 첫 검색. Router 검색어가 번역 어휘와 달라 못 찾던 질문을, 질문 원문도 함께 검색해 보완한 시도입니다. 구현 중 점수 합산 방식에서 정답이 밀리는 문제를 실제 자막으로 확인해 순위 교차 방식으로 바꿨습니다. 정답 평가셋 20문항으로 끈 실행과 켠 실행을 다시 측정했더니 1위 적중이 둘 다 16개로 같았고, 못 찾은 두 문항도 그대로였습니다. 검색만 80회에서 98회로 늘었고 LLM 호출과 토큰은 같아서 기본값은 꺼 두었습니다. 마니또처럼 못 찾던 질문이 찾아진 것은 평가셋 밖 직접 실행에서만 확인했습니다.

## 백업 — [백업] 기술 요소 정리와 Multi-Agent를 쓰지 않은 이유

[백업] 질문 대비: 기술 요소와 Multi-Agent. Multi-Agent는 호출·지연·실패 지점이 늘고 실제 원인이 구조가 아니라 어휘였기 때문에 구현하지 않았습니다. 설계안은 Supervisor, Search Agent, Verifier Agent의 허브-스포크 구조입니다.
